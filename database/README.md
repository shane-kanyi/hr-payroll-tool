# Sample data dump

`dump.sql` is a full `pg_dump` of the schema (all migrations applied
through `598c1b53ccb8`) plus sample data generated by `flask seed-demo`
(see `backend/app/seed.py`) — two teams, seven employees (one deactivated,
to demonstrate that payroll/leave history survives a soft-delete), leave
requests in every status (pending-and-escalated, approved, rejected), and
one finalized payroll period with a real unpaid-leave deduction in it.
Four demo login accounts are included (see below); the Admin account is
**not** part of this dump — it's created separately via `flask create-admin`
so the bootstrap credential is never baked into a committed file.

## Restore it

```bash
# Local Postgres:
createdb hr_payroll
psql -d hr_payroll -f database/dump.sql

# Or into the docker-compose Postgres container:
docker compose up -d db
docker compose exec -T db psql -U hr_user -d hr_payroll < database/dump.sql
```

Then create the Admin account (not included in the dump) and start the app
as usual:

```bash
cd backend && flask create-admin --email admin@example.com --password "ChangeMe123!"
```

## Regenerating this dump

```bash
cd backend
flask db upgrade
flask create-admin --email admin@example.com --password "ChangeMe123!"
flask seed-demo
pg_dump "$DATABASE_URL" --no-owner --no-privileges --clean --if-exists > ../database/dump.sql
```

`seed-demo` refuses to run twice against the same database (it checks for
an existing team first) rather than silently duplicating rows — run it
against a fresh database, not one you've already been testing against.

The two `\restrict`/`\unrestrict` lines that `pg_dump` 16.x adds
automatically are stripped from the committed file — they're a
psql-client-version-specific safety marker, not part of the actual schema
or data, and can cause `psql` clients from a different Postgres release to
choke on restore.
